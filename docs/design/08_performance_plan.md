# 08 性能検証計画

## 0. 想定規模と暫定目標（2026-11-03 回答を反映）

### 0.1 想定規模（基準ケース）

| 種別 | 構成 | 合計 |
|---|---|---|
| 月次ファイル | 3種 × 5か月 = 15ファイル、各 1,000行・20列、備考欄（約20文字） | 300,000セル、備考 約15,000件（備考列を各1列と仮定） |
| マスタファイル | 5種 × 1 = 5ファイル、各 100行・10列、備考なし | 5,000セル、対象 最大 約500件 |
| 追加取込（翌月） | 月次 3ファイル | 60,000セル、備考 約3,000件 |

この規模はメモリ（32GB）に対して十分小さく、規則による変換・検証は全件をメモリ上で処理しても問題にならない見込みである。性能上の論点は**LLM による備考の検査時間**に集中する。

### 0.2 暫定目標（提案。段階1・段階5の計測で見直す）

| 処理 | 暫定目標 | 備考 |
|---|---|---|
| アプリ起動〜プロジェクト一覧 | 10秒以内 | LLM は起動時に読み込まない |
| 取込（基準ケース20ファイル） | 30秒以内 | 原本複製・機能検出を含む |
| 計画作成・再計画 | 10秒以内 | 判断のたびに再計画するため |
| プレビュー表示・フィルタ切替 | 1秒以内 | |
| 出力＋再読込検証（20ファイル） | 1分以内 | 第二読込器（openpyxl）での検証を含む |
| LLM 列推定（初回、全列 約350列） | 10分以内（裏で実行） | 2回目以降は新しい列のみ |
| LLM 備考検査（1か月分 約3,000件） | 15分以内（裏で実行） | 計測結果が目標に届かない場合は 0.3 の対策 |

### 0.3 備考の LLM 検査を現実的な時間に収める方針

1. 備考は**異なる値ごとに1回**だけ検査する（同じ文は再検査しない。過去の作業で検査済みの文も再検査しない）。
2. 辞書置換と規則による候補検出を先に行い、既知語句を変換後表記に置き換えた文をLLMに渡す。
3. 1回の問い合わせに複数件（例：20件）の備考をまとめ、件ごとの結果をJSONで受け取る（件と結果の対応を番号で検証）。
4. 目標に届かない場合は、「辞書・規則で候補が出なかった備考のみ」「新規の備考のみ」に対象を絞る選択肢を設ける。LLM 検査を行わなかった備考は検証画面の「検査の対象外」に件数を表示する。

## 2. 合成データの条件

| 軸 | 段階 |
|---|---|
| 基準ケース | 0.1 の構成（月次15＋マスタ5）。**全計測の基本** |
| ファイル数 | 1 / 5 / 20（基準）/ 60（約1年半分。余裕の確認） |
| 1表の行数 | 100 / 1千（基準）/ 1万（余裕の確認） |
| 列数 | 10 / 20（基準）/ 50 |
| 置換列の割合 | 10% / 30% |
| 自由記述列 | なし / 1列（平均20文字。基準）/ 1列（平均100文字） |
| 対応表の規模 | 500（基準）/ 5,000 対象 |
| 自由記述の異なる値の数 | 3,000（1か月分）/ 15,000（5か月分） |
| Excel 要素 | 書式のみ / 数式あり（参照系・条件集計・文字列操作を混在。**重点**）/ 共有文字列が多い（文字列セル比率 80%） |

合成データ生成器は `tests/synthetic/` に置き、乱数の種を固定して再現できるようにする。

## 3. 計測項目

| 段階 | 指標 |
|---|---|
| 取込 | 解析時間、最大メモリ使用量、原本複製時間 |
| 範囲推定・列推定（規則） | 時間 |
| 計画作成 | 照合・採番の時間、データベース書込時間 |
| プレビュー | 初回表示時間、スクロール時の応答（仮想表示） |
| 自由記述（辞書） | 辞書構築時間、置換時間（語句数×文章量） |
| 出力 | 書出し時間、出力ファイルサイズ（元との比較） |
| 検証 | 再読込・各検査の時間（V2 の全セル比較、V7 の残存検査が重いと想定） |
| LLM（列推定） | 1列あたりの応答時間、初回読込時間、メモリ使用量 |
| LLM（自由記述） | 1件あたりの応答時間、1時間あたりの処理件数、失敗率 |

LLM は CPU / GPU / NPU（OpenVINO で利用可能な場合）、モデル規模（小・中）、量子化の組合せで計測する。**精度は合成データの正解ラベルとの一致率で記録し、実データでの精度は断定しない。**

### 3.1 段階5 の計測結果（2026-11-04、Core Ultra 7 258V）

文章の候補（合成の文章 60 件、正解つき。`python -m tests.llm.bench <モデル> <装置>`）：

| モデル（すべて int4、Apache-2.0） | 処理装置 | 読込 | 1文あたり | 検出率 | 誤った候補（60文中） |
|---|---|---|---|---|---|
| Qwen3-4B | GPU（Arc 140V） | 2.0 秒（2回目以降。初回は約15秒） | 0.28 秒 | 92.5% | 3 |
| Qwen3-4B | CPU | 10.3 秒 | 0.79 秒 | 87.5% | 4 |
| Qwen3-8B | GPU | 14.8 秒 | 0.48 秒 | 87.5% | 5 |
| Qwen3-8B（NPU 用 cw） | NPU | 32.0 秒 | 0.87 秒 | 90.0% | 12 |

基準ケース 1 か月分（売上・仕入・製造原価の備考の異なる値 331 件）を Qwen3-4B・GPU で検査：126 秒（1文あたり 0.38 秒）。AI の候補は 1 件（誤検出）で、残りの名称はすべて辞書・規則で置換済みだった。暫定目標（約 3,000 件を 15 分以内＝1文あたり 0.3 秒）に近い。3,000 件では約 19 分の見込みで、検査済みの文章は翌月以降問い合わせないため、2か月目以降は新しい文章だけになる。

列の種類（7 種の表・110 列）：Qwen3-4B・GPU で 58 秒（1表あたり約 8 秒）。

計測で分かったこと：まとめる件数（10・20・30 件）では速度はほとんど変わらず、時間の大半は出力の生成にかかる。出力の形を短くし、既知の語を伏せて渡すことで、1文あたり 0.55 秒から 0.28 秒になった。

## 4. 判断に使う観点

- 自由記述の LLM 検出が遅い場合：異なる値ごとの処理（重複除去）、既知語句の事前置換、対象列の限定、バックグラウンド実行で待ち時間を減らす。それでも不足なら「規則のみ」を既定にし LLM は任意実行にする。
- 残存検査（V7）が遅い場合：Aho–Corasick の一括検索を部品単位で並列化。
- メモリが厳しい場合：行単位の逐次処理（xlsx の XML を逐次解析）を徹底し、プレビューは作業用データベースからページ単位で読み出す。

## 5. 実施時期

- 段階1完了時（CSV 一連処理）：取込・計画・出力・検証の基礎計測
- 段階2完了時（xlsx）：Excel 要素別の計測
- 段階5（LLM）：デバイス・モデル別の計測と採否判断
