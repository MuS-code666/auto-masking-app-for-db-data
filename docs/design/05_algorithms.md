# 05 変換アルゴリズム

## 1. 全体の流れ（変換計画の作成）

1. 取込済みの各表について、確定した列規則（column_rule）を適用する。
2. 置換対象の列から「観測値」（コード、名称、コード＋名称の組）を集める。
3. 観測値を対応表と照合し（2章）、結果を次に分類する。
   - 既存対象に確定一致 → そのまま使用
   - 新規 → 仮登録し番号を確保（3章）
   - 曖昧 → 要確認項目を作成（仮登録はしない、または候補のみ）
4. 自由記述列・表外領域・見出し（指定時）に対し自由記述処理（4章）を行う。
5. セル単位の変換計画（どのセルを何に変えるか）を作成する。プレビュー・出力はこの計画だけを使う。

**計画の決定性**：同じ入力・同じ設定版・同じ対応表版からは必ず同じ計画を作る。新規対象の番号は「ファイル取込順 → シート順 → 表の範囲順 → 行順 → 列順」の初出順で確保する。

## 2. 対象の照合

### 2.1 コードがある場合（コード優先）

列規則で `role=code` かつ code_scheme が指定された列があれば、その行の対象は `(code_scheme, 元コード)` で決まる。

| 状況 | 処理 |
|---|---|
| コードが対応表にある | その対象を使う。同じ行の名称が既知の名称・別名と一致しない場合 →「同じコードに複数の名称」要確認 |
| コードが対応表にない | 新規対象として仮登録。同じ行の名称が、同種類の別の対象の名称と一致する場合 →「同じ名称に複数のコード」を情報として表示（既定は別対象） |
| 同一ファイル内で同じコードに異なる名称 | 1対象とし、名称の差異を要確認に出す（別名登録／元データの誤りとして扱う） |
| 複合キー | 要素をすべて揃えて1つのキーとして扱う。要素の一部が空欄なら「コード欠損」 |
| 参照側（売上明細の得意先CD）のコードがマスタ側（顧客マスタ）にない | 対応表上は新規対象として番号を振り置換する（コードの一貫性を保つため）。同時に関連検証で「元データの未一致」として記録し、変換で直さない |

コード比較は**文字列**で行う。`00123` と `123` は別のコード。ただし、xlsx で数値セルに表示形式で先頭ゼロを付けている場合などに備え、照合候補として「数値として等しい別表記」を要確認に出す（自動同一視しない）。

### 2.2 コードがない場合（名称で照合）

| 状況 | 処理 |
|---|---|
| 同種類の対象で、元名称・確定別名が完全一致する対象が1件 | その対象を使う |
| 完全一致が複数件（同名の別対象） | 要確認「どの対象か選択」。行内の他の列（住所等）は判断材料として表示のみ |
| 完全一致なし・正規化表記で一致する対象あり | 要確認「似た名称」（同じ対象として別名登録／別の対象） |
| 一致なし | 新規対象として仮登録（④で一括確認） |

**完全一致は表記そのもの**で判定する（全角半角・空白の違いも別表記）。正規化一致は候補提示にのみ使う。

### 2.3 コード欠損

コード列があるが空欄の行は、名称で照合（2.2）し「コード欠損」を情報として記録する。名称も空欄なら置換対象なし（空欄のまま）。

### 2.4 正規化（照合候補用）

元の値は保持したまま、以下で作る比較用の表記を使う。
- Unicode NFKC 正規化、英字の大小統一
- 空白類の除去
- 法人格表記の除去：株式会社、(株)、（株）、㈱、有限会社、(有)、合同会社 等
- 長音・ハイフン類の統一（ー －‐― 等）

正規化表記が同じになる別の対象が複数ある場合は「正規化による衝突」として要確認に出す。類似度（rapidfuzz による編集距離等）は候補の並び順に使うのみで、閾値による自動確定はしない。

### 2.5 統合・分離

- 統合：対象Bを対象Aに統合すると、Bのコード・名称がAに移り、Bは `merged`。Bの変換後名称・番号は欠番として保持し再利用しない。以後の出力ではAの変換後名称を使う。**過去の出力（Bの名称で出したもの）との表記差**を影響一覧で示す。
- 分離：対象Aの一部コード・別名を新しい対象Cへ移す。Cに新しい番号を確保する。
- いずれも master_event に記録し、対応表版を進める。

## 3. 採番

### 3.1 名称

`{name_prefix}{name_seq を name_digits 桁でゼロ埋め}` 例：顧客0001。桁数を超えたら桁を伸ばす（顧客10000）。名称番号とコード番号は**独立**に管理し、同一視しない（顧客0007 のコードが 000007 になるとは限らない）。

### 3.2 コード

コード体系ごとに、観測した元コードの形式から出力規則を作り、人が確認する。

| 元コードの形式 | 変換後コードの既定規則 |
|---|---|
| 数字のみ・固定長（例 6桁、先頭ゼロあり） | 同じ桁数の数字。元コードで使われている値と重ならない範囲から連番（例：元が 000001〜004999 なら 900000 から） |
| 英数字・接頭語あり（例 C00123） | 同じ長さ。接頭語を変換用（例 `X`）に置き換えた連番（X00001） |
| 可変長の数字 | 観測最大長に揃えた数字の連番（範囲は元と重ならないよう選ぶ） |
| 記号を含む（例 12-345） | 区切り位置を保ち、数字部分を連番 |

- **衝突回避**：変換後コードが、同じコード体系の元コード（観測済みのもの全て）と一致しないようにする。元コードと変換後コードが同じ値だと、別の対象と誤認される恐れがあるため。完全に分離できない場合（範囲が狭い）は警告し、人が規則を決める。
- **採番枯渇**：capacity（生成可能件数）から使用済み件数を引いた残りが一定割合（既定20%）を下回ったら警告、0になったら計画作成を停止し、出力規則（桁・接頭語・範囲）の変更を求める。規則を変えても既存の変換後コードは変えない。
- **型の維持**：xlsx で元が数値セルなら変換後も数値セル（表示形式は維持）。15桁を超える数字コードが数値セルで保存されている場合は、Excel の精度上すでに値が失われている可能性があるため取込時に警告する。CSV は常に文字列として扱う。

### 3.3 番号の確保と取消

- 計画作成時に新規対象を仮登録し、その場で `next_*_seq` を進める（同じトランザクションで記録）。
- 同じ作業内で再計画しても、既に仮登録済みの観測値には同じ仮登録を再利用する（番号は変わらない）。
- 判断で「既存対象へ紐付け」に変わった仮登録は `void` にし、番号は欠番となる。
- 作業の取消も同様に `void`。欠番は対応表管理画面で確認できる。

## 4. 自由記述の処理

### 4.1 辞書の構築

プロジェクトの対応表から語句辞書を作る：全種類の元名称・確定別名（status が draft/confirmed のもの）、値対応の元値、追加語句（term.action=replace）、元コード（境界条件付き）。各語句に「置換先」と「種類」を持たせる。

### 4.2 照合と置換

- Aho–Corasick 法で全語句を一度に検索し、**左から順に、重なる場合は最長一致を優先**して重ならない一致の集合を選ぶ。（例：「さくら商事」と「さくら」が両方登録されていれば「さくら商事」を優先）
- 置換は元の文字列の位置情報から**一度だけ**組み立てる。置換後の文字列を再び検索しないため、置換結果（顧客0001）の一部が別の語句に一致して再置換されることはない。
- コード：前後が英数字でない場合のみ一致とする（`123` が `1234` の一部に一致しないように）。
- 短い語（既定：2文字以下、または数字のみ4桁以下）：自動置換せず要確認に出す。人が「置換する」と確定した語は、その列（またはプロジェクト全体）で自動置換対象にする。
- 種類が曖昧な語（同じ表記が顧客名と製品名の両方にある）：要確認。列ごとに「この列では顧客を優先」の規則を設定できる。
- 規則による候補検出（LLMなしで動く）：電話番号、メール、郵便番号、URL、法人格付きの語（「〇〇株式会社」「(株)〇〇」）、敬称付きの語（「〇〇様」「〇〇御中」）。いずれも**候補**として要確認に出す。

### 4.2.1 段階4 の実装（2026-11-04）

`src/maskapp/transform/freetext.py`。

| 項目 | 実装 |
|---|---|
| 辞書 | 有効な（仮登録・確定の）対象の元名称・別名、元コード、値対応の元値。計画の作成時に、その作業で仮登録した対象を含めて作る。置換先は「対象」「コード」「値」の単位で持ち、同じ表記に置換先が複数あれば「置換先が複数の語」 |
| 照合 | 残存検査と同じ正規化（NFKC・大小統一・空白除去）を1文字ずつ行い、一致した範囲を元の文字列の位置に戻す。全角半角・空白の違いがあっても置換できる。コードだけの語は前後が英数字でない場合だけ一致 |
| 選択と置換 | 左から順に、重なる場合は最長一致。置換は元の文字列から一度だけ組み立てる（非再置換） |
| 同じ行の対象 | 置換先が複数の語は、同じ行のコード・名称の列で決まった対象が候補の1つだけなら、それを使う（例：売上明細の「さくら様より追加注文」は、その行の得意先「さくら」） |
| 短い語 | 自動で置換せず要確認（文章内の短い語）。判断（置換先を選んで置換／問題なし）は「表の定義・列」ごと |
| 置換先が複数の語 | 同じ行で決まらなければ要確認（文章内の語の置換先）。判断は「表の定義・列」ごと（4.2 の「この列では顧客を優先」に相当） |
| 規則による候補 | 電話番号・メール・郵便番号・URL・法人格付きの語（前後どちらも。㈱・(株) を含む）・敬称付きの語（様・御中・殿）に加え、「担当:〇〇」の形の担当者名。辞書で置換する範囲と重なる候補は出さない。「同様」「仕様」「お客様」「皆様」等の一般的な語は除く。判断（対象として登録・既存の対象の別名にする・値として登録・問題なし）は語句ごと（どの列でも同じ）。登録した語は以後辞書の語句になる |
| 判断の引継ぎ | 文章内の判断はすべて確定した作業から引き継ぐ。選んだ置換先が取消・統合されていれば、計画の作成時に判断し直しを求める |
| 対象 | 処理が「文章内の語句を置換」の列、表外を「文章内の語句を置換」にした表の表外のセル、xlsx のヘッダー・フッターとグラフの文字（06 章 4.3） |
| 検証 | 文章内を処理したセル・文字は、置換しなかった部分だけを残存検査する（置換後の値「顧客0001」の中の数字が短いコードに一致する等の誤検出を防ぐ）。短い語は計画で判断済みのため検証では止めない |

設計からの変更：追加語句（term 表）は使わず、候補の登録は対象の名称・別名または値対応として登録する（対応表の管理・取消の仕組みをそのまま使うため）。

### 4.3 LLM による候補検出（補助）

- 対象：自由記述列の**異なる値ごと**に1回（同じ文は重複して送らない）。
- 前処理：既知語句は変換後の表記に置き換えてから渡す（モデルに渡す元語句を減らす）。
- 入力形式：システム指示＋区切られたデータ部。データ部の内容は「検査対象の文章」とだけ扱うよう指示する。
- 出力：`[{"text": "...", "type": "会社名|人名|製品名|その他"}]` のJSONのみを受け付ける。
- 出力の検証：JSONとして読めない、または `text` が入力文章の部分文字列でない候補は捨てる。候補は要確認として人が判断する。**LLM出力を直接置換処理に使わない。**
- 失敗時：タイムアウト・異常終了・不正出力は「AI候補なし」として記録し、規則による候補検出と辞書置換で続行する。

| 項目 | 実装 |
|---|---|
| 実行 | `src/maskapp/llm/`：ワーカー（`worker.py`、起動直後に外部通信を遮断、標準入出力で1行1件の JSON）、問い合わせ（`client.py`、時間切れ・異常終了は「AI候補なし」、続けて3回失敗したら問い合わせをやめる）、内容と検証（`tasks.py`） |
| 対象 | 作業の「文章内の語句を置換」のセルの異なる値。検査済みの文章（ハッシュで識別）は問い合わせない（翌月も再利用） |
| 前処理 | 辞書の語（置換する語）と、規則で検出する候補（電話番号等）を「〇〇」で伏せてから渡す（元の語句を減らし、既知の語を答えて時間がかかるのを防ぐ） |
| 入出力 | 10 件ずつまとめて問い合わせる。出力は `{"c": [[番号, "語句", "種類"]]}`（短い形にして時間を半分にした）。「考える」出力は使わない |
| 検証 | JSON として読めない出力は捨てる。語句は前後の敬称（さん・様・氏 等）と見出し（担当: 等）を除いたうえで、渡した文章にそのまま含まれるものだけを残す。2文字未満・40文字超・伏せた印を含む語句は捨てる |
| 保存と反映 | 結果は project.db の ai_text（文章のハッシュ・モデル名・候補）。計画の作成時に、保存済みの候補を「文章内の候補（AI）」として要確認に出す（計画の作成時に AI は動かさない）。判断は規則の候補と同じ |
| 対象外の表示 | AI で検査していない文章の件数を⑤に「AI で検査していない文章があります（規則と辞書だけで検査しました）」と表示する |

### 4.4 列の種類推定（LLM補助）

- 規則：列名辞書（「得意先」「顧客」「取引先」→顧客、「品番」「製品」→製品、「単価」「金額」→維持 等）、値の形（電話・メール・日付・数値・固定長コード）。
- LLMには列名と、異なる値を最大5件（各最大50文字）だけ渡し、情報種類と処理の候補をJSONで受け取る。規則推定と食い違う場合は両方を表示し人が選ぶ。
- 実装（段階5）：③の「AI で列の種類を推定」。AI は 20 種類（顧客名・顧客コード・…・伝票番号・行番号・区分・その他）から選び、`config/suggest.py` の `spec_from_type` で列の設定の候補にする。今の設定と違う列だけを表に表示し、「AI の推定を読み込む」で設定欄に反映できる（自動では変えない）。合成データの 7 種の表（110 列）で、手で作った設定と 108 列が一致（規則の候補は 109 列）。違った2列（内線・先方担当者）は、どちらの扱いも妥当な列だった。

## 5. 整合性の維持

| 対象 | 方針 |
|---|---|
| 同一対象の一貫性 | 全ファイル・全列（自由記述を含む）で同じ変換後名称・コードを使う（対応表を唯一の根拠とする） |
| 異なる対象の区別 | 異なる対象には必ず異なる変換後名称・コード（一意制約で保証） |
| 関連（結合） | コード列は同じ対応で置換するため、元で結合できたものは変換後も結合できる。元で結合できなかったもの（未一致）は変換後も未一致のまま（直さない） |
| 行・列 | 行の追加・削除・並べ替えをしない。重複排除・名寄せ・欠損補完をしない |
| 維持列 | セルの格納値をそのまま残す（xlsx の `<v>` の文字列、CSV のフィールド文字列）。数値の再計算・再書式化をしない |
| 内容削除 | セルを空にする（xlsx：セル要素の値を削除し書式は残す／CSV：空フィールド。引用符付きで `""` だったものは `""`） |

## 6. 再実行

- 作業の再実行：同じ入力・設定版・対応表版からは同じ計画が作られる（1章の決定性）。確定済みの対応は変わらない。
- 翌月の追加ファイル：既存の確定対応を使い、新しい観測値だけ新規仮登録される。
- 出力済み作業の再出力：その作業の確定対応で再生成でき、ファイルのハッシュが記録と一致することを確認できる（xlsx は ZIP 圧縮の差でバイト一致しない可能性があるため、部品ごとの内容ハッシュで比較する）。
